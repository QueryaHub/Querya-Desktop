# Архитектура плагинов и расширений для Flutter Desktop

Flutter по умолчанию компилирует код в AOT (Ahead-of-Time), что делает невозможным динамическую подгрузку сырого Dart-кода или использование механизмов вроде `Isolate.spawnUri` в релизных сборках на десктопе. 

Тем не менее, для создания мощной системы плагинов (аналогично VS Code или Obsidian) существует несколько проверенных архитектурных подходов.

---

## 1. Мультипроцессная архитектура (RPC через Stdio)
*Идеально подходит для драйверов баз данных, форматтеров, линтеров и тяжелой логики.*

Это подход, который использует VS Code для Language Servers. Главное приложение (Host) запускает плагин как отдельный бинарный процесс и общается с ним.

**Как это работает:**
- Плагин представляет собой исполняемый файл (написанный на Dart, Rust, Go и т.д.).
- Flutter вызывает `Process.start('plugin_executable')`.
- Общение происходит через `stdin`/`stdout` с использованием протокола **JSON-RPC 2.0**.
- В Dart для этого используются пакеты `json_rpc_2` и `stream_channel`.

**Плюсы:**
- **Абсолютная изоляция:** Падение плагина не "положит" главное приложение.
- **Языконезависимость:** Разработчики могут писать расширения на любом языке (Python, Node.js, Go).
- **Многопоточность ОС:** Тяжелые вычисления происходят вне изолятов Flutter.

**Минусы:**
- Сложно интегрировать UI-компоненты (только обмен данными).
- Оверхед на сериализацию/десериализацию JSON-RPC.

---

## 2. Исполнение байткода (dart_eval / flutter_eval)
*Идеально подходит для UI-плагинов и скриптов.*

Пакет `dart_eval` представляет собой независимый компилятор и виртуальную машину для Dart. Он позволяет компилировать подмножество Dart в собственный байткод (`.evc`) и выполнять его в рантайме.

**Как это работает:**
- Разработчик расширения пишет код на Dart (поверх специального API вашего приложения).
- Код компилируется в байткод `.evc`.
- Приложение скачивает `.evc` файл и загружает его через движок `flutter_eval`.

**Плюсы:**
- Плагины пишутся на родном **Dart**.
- Поддержка создания **Flutter виджетов** прямо из плагина.
- Работает внутри процесса без необходимости создавать RPC.

**Минусы:**
- `dart_eval` поддерживает не весь синтаксис Dart (есть ограничения).
- Производительность ниже, чем у скомпилированного AOT кода.

## 3. WebAssembly (WASM) песочницы
*Современный подход для кроссплатформенной логики.*

Использование пакетов наподобие `wasm3` или встроенных механизмов для загрузки `.wasm` модулей в рантайме. 

**Как это работает:**
- Плагин пишется на Rust, C++ или Dart (с поддержкой WASM-GC) и компилируется в `plugin.wasm`.
- Приложение загружает байткод в WASM-машину, маппит функции и выполняет вызовы.

**Плюсы:**
- **Высочайшая безопасность (Sandbox):** WASM по умолчанию не имеет доступа к сети и ФС.
- **Производительность:** Почти нативная скорость.

**Минусы:**
- Сложно прокидывать сложные объекты (например, виджеты или потоки). В основном общение идет числами и массивами байт.

---

## 4. Встроенные скриптовые движки (QuickJS / Lua)
*Альтернатива для легкого скриптинга.*

Вы можете встроить движок JavaScript (через пакет `flutter_qjs`) или Lua (`lua_dardo`).
- Пользователи пишут JS/TS скрипты для форматирования SQL, генерации запросов и т.д.
- Вы биндите функции Dart в контекст JS.
- **Плюс:** JavaScript знают все, низкий порог входа для авторов плагинов.

## Рекомендованный гибридный подход для Querya

Так как Querya — это клиент баз данных, вам понадобятся плагины разного типа. Идеальная архитектура должна комбинировать подходы:

1. **Для новых драйверов БД и тяжелых задач** -> **Мультипроцессная RPC архитектура**. Плагин-драйвер для MongoDB или Redis скачивается как бинарник, стартует в фоне, а Querya общается с ним по JSON-RPC. Это защитит от падения клиента из-за утечки памяти в драйвере.
2. **Для кастомных виджетов, анализаторов и сниппетов** -> **dart_eval** или **Встроенный QuickJS**. Пользовательские скрипты, которые безопасно модифицируют запросы перед отправкой, можно писать прямо в приложении на JavaScript или Dart.
3. **Для тем и настроек** -> Текущий подход **JSON/YAML деклараций** (он уже отлично спроектирован).

## Жизненный цикл плагина в Querya
1. **Discovery (Поиск):** Чтение `manifest.json` из папки `~/.querya/extensions/`.
2. **Activation:** Приложение читает тип расширения. Если это RPC — делает `Process.start`. Если это Eval — парсит байткод.
3. **Registration:** Плагин регистрирует свои "провайдеры" в ядре (например, `PluginRegistry.registerDbDriver('mongo', processChannel)`).
4. **Deactivation:** При удалении или выключении — вызов `process.kill()` или очистка VM контекста.

## Как реализовать плагины баз данных (Core + UI) в AOT Flutter?

Если плагин (например, для ClickHouse или Cassandra) должен не только выполнять запросы (Core), но и добавлять свои формы подключения, иконки и меню (UI), использование AOT компиляции бросает вызов: **нельзя просто "скачать" новые Flutter-виджеты в рантайме** (кроме `dart_eval`, который ограничен).

Для решения этой задачи в enterprise-приложениях (включая VS Code) используется паттерн **Extension Points (Точки расширения) + Server-Driven UI (SDUI)**.

### 1. Декларативный UI (Server-Driven UI)
Вместо того чтобы плагин присылал готовый Flutter-виджет, он присылает **JSON-схему** своего интерфейса, а ядро Querya Desktop ее отрисовывает.
Например, при активации плагин ClickHouse отправляет ядру структуру формы подключения:
```json
{
  "type": "connection_form",
  "fields": [
    { "id": "host", "type": "text", "label": "Host", "required": true },
    { "id": "http_port", "type": "number", "label": "HTTP Port", "default": 8123 },
    { "id": "use_ssl", "type": "checkbox", "label": "Use SSL" }
  ]
}
```
Ядро Flutter читает этот JSON и динамически генерирует `TextFormField` и `Checkbox` из дизайн-системы (shadcn_flutter). Когда пользователь жмет "Connect", ядро собирает `Map<String, dynamic>` с введенными данными и отправляет RPC-запрос в процесс плагина: `rpcClient.send('connect', formData)`.

### 2. Точки расширения (Extension Points)
Ядро приложения должно заранее иметь "слоты", куда плагин может встроиться:
- **`SidebarTree`**: Плагин по RPC сообщает, какие узлы (Databases, Tables, Column Families) отрисовать в дереве.
- **`ConnectionForm`**: Плагин отдает JSON для генерации формы.
- **`ContextMenu`**: Плагин может попросить добавить кнопку "Run ClickHouse Optimize" в контекстное меню таблицы.

### Идеальный пайплайн для новых БД:
1. **Манифест (`package.json` или `manifest.yaml`)**: В корне расширения лежит файл, который говорит ядру: *"Я добавляю новую БД 'ClickHouse'. Вот путь к моей иконке `icon.svg`."*
2. **UI слой (Flutter Core)**: Читает манифест, добавляет ClickHouse в список доступных БД, рисует иконку. При клике запрашивает у плагина форму подключения по RPC (или читает ее из того же манифеста).
3. **Core слой (RPC Процесс)**: Отдельный бинарник (на Dart/Go/Rust), который устанавливает сетевое соединение с ClickHouse, принимает SQL-запросы от Flutter по RPC, отправляет их в базу и возвращает результаты в виде стандартизованного JSON-массива.

Таким образом, UI остается абсолютно нативным (Flutter), а вся сложная, потенциально падающая логика работы с сетью и бинарными протоколами вынесена в безопасный RPC-процесс плагина.
