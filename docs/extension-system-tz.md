# ТЗ: Архитектура системы расширений и Маркетплейса (Querya Desktop)

## 1. Концепция и Ограничения
**Цель:** Превратить Querya Desktop из монолитного клиента баз данных в расширяемую платформу (подобно VS Code или DBeaver), позволяющую сторонним разработчикам добавлять поддержку новых СУБД (ClickHouse, Cassandra, Redis), форматировщиков и UI-тем.

**Главное техническое ограничение:** Querya Desktop написан на Flutter, который на десктопе компилируется в машинный код (AOT). Это делает невозможным динамическую загрузку сырого Flutter/Dart кода в рантайме.
**Решение:** Гибридная архитектура, сочетающая **Мультипроцессность (JSON-RPC)** для бизнес-логики и **Декларативный UI (Server-Driven UI)** для отрисовки интерфейсов.

---

## 2. Высокоуровневая архитектура (Блоки системы)

Система делится на 4 независимых блока, каждый из которых отвечает за свою зону:

### Блок A: Core Host (Ядро Flutter)
Главное монолитное приложение Querya Desktop.
* **Ответственность:**
  * Управление жизненным циклом расширений (запуск, остановка процессов).
  * Парсинг конфигураций (JSON) и динамическая отрисовка интерфейсов (SDUI).
  * Безопасное хранение секретов (кредов баз данных).
  * Рендеринг таблиц результатов (TableView) и SQL-редактора.

### Блок B: Marketplace Client (Менеджер пакетов)
Встроенный в ядро модуль для работы с удаленным сервером маркетплейса.
* **Ответственность:**
  * Запросы к API маркета (поиск, тренды, обзоры).
  * Скачивание `.zip` архивов расширений.
  * Валидация безопасности (сверка `sha256` хеш-сумм).
  * Установка, распаковка и обновление версий локально.

### Блок C: RPC Protocol Bridge (Транспортный слой)
Прослойка между Flutter-интерфейсом и внешним бинарным плагином.
* **Ответственность:**
  * Сериализация и десериализация команд в стандарт **JSON-RPC 2.0**.
  * Передача потоков через `stdin`/`stdout` запущенного процесса.
  * Обработка крашей (если плагин упал с Segfault, мост должен перехватить ошибку и перезапустить его, не убив само приложение Querya).

### Блок D: External Plugin Process (Внешний плагин)
Отдельный исполняемый файл (бинарник), написанный на Dart, Rust, Go или C++.
* **Ответственность:**
  * Содержит драйвер целевой БД (например, нативный клиент ClickHouse).
  * Устанавливает TCP/HTTP соединение с реальной базой данных.
  * Выполняет запросы от ядра и возвращает стандартизованные наборы данных (Rows/Columns).
  * Сообщает ядру, *как* должен выглядеть интерфейс (передает JSON схемы).

## 3. Декларативный UI (Server-Driven UI) и Extension Points

Так как плагин не может отправлять готовые Flutter-виджеты, ядро предоставляет "Слоты" (Extension Points). Плагин отправляет JSON, а ядро его рендерит.

### 3.1. Connection Form (Форма подключения)
Плагин декларирует структуру полей, необходимых для подключения.
* **Пример JSON от плагина:**
  ```json
  {
    "extension_point": "connection_form",
    "fields": [
      { "id": "host", "type": "string", "label": "Host", "required": true },
      { "id": "http_port", "type": "number", "label": "HTTP Port", "default": 8123 },
      { "id": "use_ssl", "type": "boolean", "label": "Use SSL", "default": false },
      { "id": "auth_type", "type": "select", "options": ["Basic", "Token"] }
    ]
  }
  ```
* **Действие ядра:** Flutter генерирует текстовые поля, чекбоксы и дропдауны (используя дизайн shadcn_flutter). При нажатии "Connect" собирает `Map` и шлет по RPC: `{"host": "localhost", "http_port": 8123...}`.

### 3.2. Sidebar Tree (Дерево обозревателя)
Плагин управляет структурой боковой панели.
* **Пример JSON от плагина:**
  ```json
  {
    "extension_point": "sidebar_tree",
    "nodes": [
      { "id": "tables", "label": "Tables", "icon": "table", "expandable": true },
      { "id": "dictionaries", "label": "Dictionaries", "icon": "book", "expandable": true }
    ]
  }
  ```
* **Действие ядра:** Рендерит узлы. При клике на "развернуть" шлет RPC-запрос `fetchTreeChildren("tables")` в плагин.

### 3.3. Context Menus & Toolbars (Контекстные меню)
* Плагин может запрашивать добавление пунктов в меню (например, `id: "ch_optimize_table"`, `label: "Optimize Table"`).
* При клике пользователя Flutter шлет команду в плагин: `executeCommand("ch_optimize_table", { tableName: "users" })`.

## 4. Жизненный цикл плагина базы данных

1. **Discovery (Обнаружение):** При старте Querya Desktop сканирует папку `~/.querya/extensions/` и читает файлы `manifest.json`.
2. **Registration (Регистрация):** Если найден драйвер (например, `querya-clickhouse-plugin`), он добавляется в список доступных баз в UI.
3. **Activation (Запуск процесса):** Когда пользователь нажимает "Создать подключение ClickHouse", ядро делает `Process.start('~/.querya/extensions/clickhouse/plugin.exe')`.
4. **Handshake (Рукопожатие):** Процесс запускается, ядро и плагин обмениваются версиями протокола JSON-RPC и проверяют совместимость.
5. **UI Request:** Ядро запрашивает `getConnectionSchema()`. Плагин отдает JSON формы.
6. **Execution (Работа):** Форма заполнена. Ядро шлет `connect(credentials)`. Далее идут запросы `executeSql()`, плагин возвращает данные таблиц.
7. **Termination (Остановка):** При закрытии приложения или соединения, ядро шлет команду `shutdown()`, а затем вызывает `process.kill()` для очистки ресурсов ОС.

## 5. Структура манифеста (`manifest.json`)

Каждое расширение должно содержать манифест, по которому работает Маркетплейс и Ядро:

```json
{
  "id": "queryahub.clickhouse-driver",
  "name": "ClickHouse Database Driver",
  "version": "1.0.0",
  "publisher": "QueryaHub",
  "type": "database_driver",
  "engines": {
    "querya_desktop": "^0.5.0"
  },
  "main": "bin/clickhouse_plugin",
  "icon": "assets/icon.svg",
  "description": "Full support for ClickHouse databases including Dictionaries and Materialized Views."
}
```

## 6. Безопасность (Security & Sandboxing)

Поскольку плагины могут быть загружены из сторонних источников, безопасность — приоритет.

1. **Валидация источника:** Маркетплейс возвращает `sha256Checksum` для скачиваемого архива. Клиент прерывает установку, если хеш не совпадает.
2. **Управление секретами (Credentials):** Плагин **не должен** сам сохранять пароли на диск. Плагин получает пароль/токен от ядра только в оперативной памяти в момент вызова метода `connect()`. Ядро Querya (Flutter) полностью отвечает за шифрование и хранение паролей в `flutter_secure_storage`.
3. **Права процесса:** (Опционально на будущее) Запуск процесса плагина в ОС с пониженными правами (без доступа к пользовательским файлам), чтобы плагин не мог прочитать личные данные пользователя.
